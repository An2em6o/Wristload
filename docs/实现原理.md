## 1. 项目总览与架构分层

Wristload-Next 是一个 Flutter Material 3 桌面应用，用于向小米 Vela 手表/手环（如手环 9）**安装表盘（.bin）与快应用（.rpk）**、读取设备状态并传输设备日志。应用整体分四层，职责严格分离：

| 层 | 目录 | 职责 |
|---|---|---|
| 应用层 | `lib/application/` | `DeviceController` 核心状态机（扫描/连接/鉴权/传输/安装协调、错误处理、会话生命周期）、诊断日志服务、主题与浮动窗口协调 |
| 领域层 | `lib/domain/` | 纯逻辑：`protocol/` 协议编解码（L1/L2、鉴权、Mass、ZAU）、设备档案、安装模型与检查点、固件包检查、偏好与设备存储 |
| 平台层 | `lib/platform/` | 平台适配：`BleTransport`（统一蓝牙接口）、V2 连接准备（Linux/macOS/Windows）、authkey 安全存储、文件选择 |
| 表现层 | `lib/presentation/` | Flutter UI 页面与对话框（设备列表、设备信息、环境详情、诊断日志、浮动安装窗口等） |

另有：

- `plugins/wristload_rfcomm_linux/`：Linux 经典蓝牙 RFCOMM/SPP 原生插件（C++，走 BlueZ D-Bus）；
- `plugins/bluetooth_low_energy_windows/`：Windows BLE 适配（vendor 插件）；
- `plugins/desktop_drop/`：桌面拖放支持；
- `linux/runner/`：GTK 嵌入器（`my_application.cc`）；
- `tool/`：构建脚本、页面注册表生成器、HCI 抓包检查工具；
- `.github/workflows/build-linux.yml`：x86-64 自动构建 + deb 打包 + Release。

**典型数据流**：UI 事件 → `DeviceController` → 协议层（domain）→ `BleTransport` → 原生插件 → 蓝牙设备；设备数据反向流回 UI（通过 `ChangeNotifier` 通知）。

## 2. 蓝牙基础：扫描与经典蓝牙 RFCOMM

**扫描（BLE）**：应用通过 BLE 扫描发现手环（`BleTransport.startScan()` → `CentralManager.startDiscovery()`），广告数据用于识别设备身份与名称；扫描结果按 `DeviceProfile` 匹配型号。

**连接（桌面 V2 设备——手环 9 系）**：主传输是**经典蓝牙 RFCOMM/SPP**，而不是 BLE GATT：

- BLE 仅用于发现与身份匹配（MAC/标识符）；
- 点击设备后，平台层执行：
  - **Linux**：BlueZ 建立经典蓝牙配对（`AgentManager1` 注册 NoInputNoOutput agent，自动确认授权）→ `ProfileManager1` 注册 SPP Profile（UUID `00001101`）→ `Device1.ConnectProfile` 让 BlueZ 解析 SDP 并交付已连接 socket；
  - **macOS**：CoreBluetooth 扫描 + IOBluetooth SPP（配对由系统处理）；
  - **Windows**：BLE 连接 + 系统配对流程，RFCOMM 建链等待系统配对完成。
- RFCOMM 建链成功后进入 SPP 协议会话（见下节）。

**免扫描直连**：已保存的设备（`LastDeviceStore` 持久化身份）可点击直连——构造 `_PersistedPeripheral` 直接发起 RFCOMM，跳过 BLE 扫描。

## 3. SPP / L1 / L2 传输协议

SPP 通道上的协议是手环 9 系（miwear-core `TransportL1`）的 App 版 L1 帧，全部小端。

**L1 帧格式**（8 字节头 + payload）：

```
[A5 A5][(frx<<4)|type][seq][len(LE)][crc16(LE)] [payload]
```

- `type`：1=ACK、2=CMD、3=DATA；
- `crc16`：CRC-16/ARC（反射多项式 0xA001，与官方 TABLE_16 一致）；
- ACK 帧：type=1 无 payload（V2 固定 `A5 A5 01`）。

**L1START 会话协商**：CMD 帧（type=2）`cmd=1` + 21 字节 config（VERSION=1.0.0、MPS=0xFC00、TX_WIN=32、SEND_TIMEOUT=10000）→ 设备回 `L1START_RSP`（cmd=2）→ L1 会话建立，随后进入鉴权。

**L2 载荷**（DATA 帧 payload = `[channel][opCode][protobuf]`）：

| channel | 用途 |
|---|---|
| 1（PB） | protobuf 业务命令（鉴权、设备状态、ZAU 命令） |
| 2（Mass） | 文件分片（表盘/快应用安装） |
| 3（MassVoice） | 语音分片 |
| 4/5（FileSensor / FileFitness） | 传感器 / 健身文件（V1 设备日志） |
| 6（Ota） | 官方保留的固件 OTA 通道（仅协议标识，不发送） |

- `opCode`：1=WRITE（明文）、2=WRITE_ENC（加密，见第 5 节）；
- protobuf wire 为**自实现最小编码器**（varint / length-delimited / fixed32），int 字段的 varint/zigzag 语义待真机验证，通过 `IntEncoding` 保留切换能力。

**SPP 版本查询**：连接后先发 App SppVersionReader 同款 `BA DC FE` 版本查询帧，V1 设备回 type=106 版本包（payload 为可打印 ASCII 或数值字节）；V2 设备不应答，2 秒超时后直接进入 L1START，不影响鉴权。

## 4. 鉴权握手（WearAuthV2）

**传输层**：RFCOMM → L1START → L2(PB, 明文) → `abu` protobuf。实现依据为官方 App 3.57.0 `WearAuthV2`/`abu`/`bc0`/`hc0`/`nc0`/`ec0` 与真机 SPP 日志（不混用 Gadgetbridge 的直写消息结构）。

**命令体系**（`XiaomiAuth`，对应 zau e=1）：

| f | 名称 | 作用 |
|---|---|---|
| 5 | cmdSendUserId | WearAuthV1：直接发送 userId |
| 26 | cmdNonce | WearAuthV2 step1：发送 phoneNonce 验证请求 |
| 27 | cmdAuth | WearAuthV2 step3：发送 AuthStep3（加密设备信息） |

**流程**：

1. **f=26**：构建 `abu{e=1, f=26, bc0.field30=hc0}`——本地绑定模式（手环 9）**必须携带 appDeviceId**（固件已存绑定 appDeviceId，缺则忽略报文）；仅使用 authkey，不要求小米账号；
2. 设备回包 `bc0`（field31=verify 响应）——含 watchNonce、设备签名等；
3. **f=27**：校验设备签名 `HMAC(DeviceKey, watchNonce‖phoneNonce)` == watchHmac → 用 HKDF 派生会话材料 → 发送 AuthStep3。

**密钥派生（HKDF）**：输出 40 字节，布局为 `DeviceKey(16) + AppKey(16) + DeviceIV(4) + AppIV(4)`。

**设备信息加密**：`pe0{field1=0, field2=SDK(float), field3=model, field4=appCapability, field5=region}`——用 `AES-CCM(AppKey, nonce=AppIV‖0‖0, mac=32bit)` 加密后放入 `ec0{signApp=1, encryptedCompanionDevice=2}` → `bc0.field32`。

**回包解析**：`abu → bc0` 的 field31=verify 响应、field33=confirm 响应，用于推进握手状态机。

## 5. 会话加密（AES-CTR）

已鉴权会话的业务帧使用 **AES-CTR**（`AES/CTR/NoPadding`）：

- **初始块 = 同方向 16 字节密钥本身**，没有额外的包计数器字段；
- 发送方向用 **AppKey**，接收方向用 **DeviceKey**；
- 加密层只负责字节变换，发送由传输控制器统一封装（L2 `opCode=WRITE_ENC`）。

## 6. 设备状态与固件版本

**设备状态查询**（ZAU `basicStatus`，e=2）：

| 子命令 | 内容 |
|---|---|
| 1 | 电量（`batteryPercent`） |
| 62 | 存储（`storageUsedBytes` / `storageTotalBytes`） |
| 3 | 系统时间同步（TimeSyncer 的 `setSystemTime`） |

**电量（GATT 路径）**：标准 Battery Service（0x180F / 特征 0x2A19）读取；空值或异常值保持未知而不是显示假电量。

**固件版本**：

- **GATT 版本特征** `00000050`（fe95 服务）——Android/macOS 读取；首字节 0 判定为 V1（旧传输）、非 0 为 V2（新传输）；
- **SPP type=106 版本回包**——V1 设备响应版本查询后返回（payload 为可打印 ASCII 如 `2.1.2`，或数值字节）；
- **Linux 限制**：手环 9 的 fe95 服务不暴露给 BlueZ（GATT 枚举不到），V2 设备又不响应 SPP 版本查询——因此 **Linux 上 V2 设备的固件版本无法读取**（平台限制，UI 已明确标注，而非故障）。

## 7. 资源安装流程（表盘 / 快应用 / Mass）

**ZAU 命令体系**（`zau`：f1=命令号 e、f2=子命令 f、oneof 载荷）：

| 对象 | 命令（e） | 子命令（f） |
|---|---|---|
| 表盘 setFace | 4 | 0=列表、1=激活、2=卸载、4=预装、5=安装结果、14=获取 |
| 快应用 appList | 20 | 0=列表、1=预装（prepareInstallApp）、2=安装结果、3=卸载、4=启动 |
| Mass 文件传输 | 22 | MassPrepare / MassData / 取消（o1h） |

**表盘（.bin）安装流程**：

1. **预装**：`zau e=4 f=4`（`y8u` 表盘文件信息——faceId/fileSize 等）→ 设备回 `z8u`（预装结果——`expectedSliceLength` 建议分片长度、可覆盖标记）；
2. **Mass 传输**：`e=22`——`s1h` MassPrepare（dataType/MD5/fileLength）→ `u1h` 响应（`expectedSliceLength`）→ 在 channelMass 上分片发送；
3. **安装结果**：`e=4 f=5`（`x8u`——id/code）；
4. **激活**：`setFace`（`e=4 f=1`）设置当前表盘。

**快应用（.rpk）安装流程**：

1. **预装**：`e=20 f=1`（`j8s`——packageName/versionCode/packageSize）→ `k8s` 响应（expectedSliceLength）；
2. **Mass 传输**：Mass `0x40` 分片；
3. **结果**：等待匹配包名的 `e=20 f=2`（`l8s` 安装结果）。

**Mass 分片协议**（对照官方 `MassDataDispatcher` / `MassDataSplitter`）：

- 文件按 **10 MiB** 分成 pending message；
- 首个 pending message 在文件数据前加 **22 字节头**（dataType / MD5 / fileLength / sentLength）；
- 最后一个 pending message 末尾加 **CRC32**（覆盖首头 + 从断点起的文件数据）；
- 每个发送 payload 前 4 字节为小端 `总片数:uint16, 片序号:uint16`；
- 协商的 `segmentLength` 包含这 4 字节，每片正文最多 `segmentLength - 4` 字节；
- **设备 ACK 驱动双层进度条**（KB 进度 + KB/s 实际确认速度）；
- 支持本地取消、超时停止、**检查点**与重连后的源文件一致性（MD5）检查。

## 8. 设备日志传输

- 设备日志分片格式：`[version=0][command][total:uint16][sequence:uint16][data]`；
- command：**129**=deviceLog、**130**=oneTrackLog（V1 通道 4/5 → 103/104，V2 通道 2 → 104）；
- 请求：ZAU `deviceLog e=2 f=80`（start）/ `f=81`（result 完成通知）；
- 分片头 6 字节 + 文件保留头 5 字节 + CRC32 4 字节；
- **HCI/btsnoop 解码器**（`hci_decoder.dart`）：解析记录方向、ACL/L2CAP/RFCOMM 分段，再从 L1 流恢复会话与加密帧——用于离线检查/取证，不访问网络、不保存 authkey、不产生蓝牙写入（上限 512 MiB）。

## 9. Linux 插件实现（BlueZ D-Bus）

`plugins/wristload_rfcomm_linux`（C++）实现与 Android 原生桥相同的通道契约：

- MethodChannel `wristload/rfcomm`：`ensurePermissions` / `pair` / `connect` / `write` / `disconnect`；
- EventChannel `wristload/rfcomm/events`：二进制数据包 + `rfcomm_closed` / `rfcomm_read` 错误。

**技术栈**（系统总线 `org.bluez`）：

- **设备解析**：`ObjectManager.GetManagedObjects` 按 Address 解析设备路径（`resolve_device_path`，先临时 StartDiscovery 再轮询）；
- **配对**：`AgentManager1` 注册 NoInputNoOutput agent（自动确认授权请求）；
- **SPP 连接**：`ProfileManager1` 注册客户端 Profile（服务 UUID `00001101`）→ `Device1.ConnectProfile` 让 BlueZ 解析 SDP → 回调 `NewConnection` 交付已连接 socket fd；
- **线程模型**：GDBusConnection / agent / profile 在 Flutter/GTK 主线程导出（入站 D-Bus 调用走主循环）；pair/connect 在 worker 线程用同步 D-Bus 调用；数据读取在**专用 reader 线程**；fd 通过 `pending_fd` + 条件变量从主线程交接给 worker；
- 超时与轮询：配对 30s、连接 25s、解析轮询 500ms；
- 会话用 `generation` 计数使失效连接的回调被忽略，保证断开/重连时序正确。

## 10. 平台适配层（BleTransport）——各平台差异分开说明

`BleTransport` 是统一的蓝牙接口（扫描、RFCOMM 写/读、GATT 特征读取、配对等），底层按平台路由到不同的实现。**平台差异是本文档最重要的区分点**：

| 能力 | Linux | macOS | Windows | Android |
|---|---|---|---|---|
| BLE 扫描 | `bluetooth_low_energy` 插件（`CentralManager.startDiscovery`） | CoreBluetooth | `bluetooth_low_energy_windows`（vendor 插件） | `flutter_blue_plus` 风格桥 |
| 经典 RFCOMM/SPP | **本地插件** `wristload_rfcomm_linux`（BlueZ D-Bus） | IOBluetooth SPP | 系统配对后 RFCOMM | 原生 RFCOMM 桥 |
| GATT 特征读取 | ❌ 不支持（手环 9 的 fe95 不暴露给 BlueZ） | ✅ CoreBluetooth | ✅ vendor 插件 | ✅ |
| authkey 存储 | Secret Service（libsecret） | Keychain | 系统凭据 | 安全存储 |
| 配对流程 | BlueZ Agent（NoInputNoOutput 自动确认） | 系统 TCC + 配对弹窗 | 系统配对（RFCOMM 等待配对完成） | 系统配对 |

**扫描幂等差异**：

- **Linux**：`startScan` 对 BlueZ 的 `InProgress` / `AlreadyExists` 按**幂等成功**处理（扫描已在运行时不再报错）；`stopScan` 对 `No discovery started` 幂等（BlueZ 连接后可能自动结束 discovery）；
- **macOS**：启动扫描前先处理 TCC 授权状态（`authorize`），避免授权弹窗与扫描竞争产生 `permission_pending` 瞬时失败；
- **Windows**：依赖 vendor 插件的 `CentralManager`，GATT 事务偶发未就绪时按重连重试（最多 8 轮服务发现）。

**V2 连接准备**（`DesktopV2Connection` 接口，各平台独立实现）：

- `LinuxV2Connection`：直接返回 `pairDevice` 结果——配对与 SPP 建链都由 BlueZ 在 RFCOMM 阶段完成；
- `MacosV2Connection`：在 prepare 阶段解析配对/身份（CoreBluetooth UUID 不是经典设备身份，须先解析）；
- `WindowsV2Connection`：配对仪式在 `connectRfcomm` 内执行（系统配对对话框）。

## 11. UI 层（presentation）

表现层是 Flutter 页面，全部由 `DeviceController`（`ChangeNotifier`）驱动，通过监听器重建：

- **设备列表（home）**：扫描结果 / 已保存设备入口、连接入口、状态提示；
- **设备信息页**（`device_info_page.dart`）：型号、固件版本（Linux 上 V2 显示平台限制提示）、MAC/标识、连接方式、authkey、存储/电量、断开与删除；
- **环境详情对话框**（`device_environment_details_dialog.dart`）：连接状态、型号、固件版本、同步状态等调试信息；
- **连接警告对话框**（`connection_warning_dialog.dart`）：平台配对注意事项（如 Linux 的经典蓝牙配对提示）；
- **固件检查对话框**（`firmware_inspection_dialog.dart`）：`firmware_package_inspector` 的检查结果展示；
- **诊断日志窗口**（`diagnostic_log_window_app.dart` + `diagnostic_log_service.dart`）：分类/级别过滤的实时日志（也是排查协议问题的主要入口）；
- **浮动安装窗口**（`floating_install_window_app.dart`）：独立小窗口悬浮显示安装进度（双层进度条、KB/s）；
- 主题：`app_theme.dart` + `theme_controller.dart`（亮/暗主题跟随系统或手动）。

## 12. 持久化与安全存储

| 存储 | 机制 | 内容 |
|---|---|---|
| authkey | Secret Service（Linux）/ Keychain（macOS）/ 安全存储 | 绑定 token（32 位 hex），按设备保存，可删除 |
| 上次设备（`last_device_store`） | shared_preferences | 设备身份（免扫描直连用） |
| 已知设备（`known_devices_store`） | shared_preferences | 历史设备列表（含 authkey 候选解析） |
| 安装检查点（`install_checkpoint_store`） | shared_preferences | 断点续传状态 |
| 偏好（transfer/auto_connect/oobe/floating_window/diagnostic_log） | shared_preferences | 用户设置 |

**authkey 来源**：`device_tools.dart` 从用户提供的设备列表快照/日志中解析（`AuthKeyCandidate`——按 MAC 去重取最新记录），或由用户手动输入；不保存会话材料，只存身份与密钥。

## 13. 构建与 CI

**本地构建**：

- `tool/build_linux.sh`（debug / release——先生成页面注册表再构建）；
- `tool/build_deb.sh`（arm64 / amd64 deb 打包，版本号取自 pubspec）；
- `tool/build_windows_only.ps1` 等（Windows 构建 + 页面注册表更新）；
- `tool/generate_page_registry.dart`（生成页面注册表，CI 与本地共用）。

**CI（GitHub Actions）**：`build-linux.yml` 当前构建 Linux x86-64；计划改为 **matrix 多平台**（Linux x64 + Windows + macOS）——每次 push/手动触发时**同时构建所有支持的系统并打包**（Linux deb、Windows/macOS zip），各平台产物分别上传并发布到对应版本号 Release（详见下一节说明）。

## 14. 已知限制

- **Linux 固件版本**：V2 设备（手环 9）的 GATT fe95 不暴露给 BlueZ，SPP 版本查询又不响应——Linux 上无法读取 V2 固件版本（UI 已标注）；
- **Linux GATT**：无 GATT 特征读取能力（影响版本特征、电量特征读取等）；
- **协议待验证**：protobuf int 的 varint/zigzag 语义（`IntEncoding` 保留切换）；OTA 通道（`channelOta`）仅作协议标识，**不发送固件**；部分命令（如 FactoryTest）仅供取证，不主动发送；
- **平台验收状态**：Linux/Windows/macOS 已接入主链路，真机安装验收进度见 README「当前能力」；
- **模拟器/调试**：Linux 桌面会话需可访问系统总线蓝牙（BlueZ）；无图形会话时 RFCOMM 相关功能不可用。
